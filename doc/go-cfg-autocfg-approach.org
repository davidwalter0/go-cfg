* Executive Summary

This document outlines the integration strategy between go-cfg and AutoCfg systems to create a unified, powerful configuration management solution. The integration leverages the complementary strengths of both systems: AutoCfg's sophisticated file discovery and loading mechanisms with go-cfg's advanced flag processing and clean naming conventions.

* System Analysis Summary

** AutoCfg Strengths
- **Flexible Search Strategies**: Union (merge all) vs First (stop on first found) modes
- **Hierarchical Discovery**: Standard locations (=/etc=, =~/.config=, local, environment override)
- **Indirect Configuration**: Pointer files that reference actual config locations
- **Environment Integration**: Variable expansion and tilde resolution
- **Multi-source Merging**: Union dominance with clear precedence rules

** go-cfg Strengths  
- **Clean Flag Naming**: FlatNest() generates intuitive flags (=--api-host= vs =--config-api-host=)
- **Advanced pflag Integration**: Superior command-line argument processing
- **Type Safety**: Robust struct tag processing and automatic type conversion
- **Enhanced Help**: Environment variable display and comprehensive usage text
- **Validation**: Required field checking and default value handling

* Integration Approaches

** Approach 1: Layered Integration (Immediate Implementation)

*** Overview
Maintain both systems as separate packages but compose them in a layered architecture where AutoCfg handles file discovery/loading and go-cfg handles flag processing.

*** Implementation
#+begin_src go :tangle /home/david/org/go-cfg/doc/layered-integration-example.go :results org :main no :package 'discard :mkdirp yes :tangle-mode o0644
package main

import (
    "log"
    "github.com/davidwalter0/go-cfg"
    "github.com/davidwalter0/go-configurator/pkg/autocfg"
)

type Config struct {
    ServiceName string `json:"service_name" required:"true"`
    API struct {
        Host string `json:"host" default:"localhost"`
        Port int    `json:"port" default:"8080"`
    } `json:"api"`
    Database struct {
        Host string `json:"host" default:"localhost"`
        Port int    `json:"port" default:"5432"`
        Name string `json:"name" required:"true"`
    } `json:"database"`
}

func main() {
    var config Config
    
    // Stage 1: AutoCfg handles file discovery and loading
    // Searches /etc, ~/.config, local directory, $AUTOCFG_FILENAME
    if err := autocfg.Configure(&config); err != nil {
        log.Printf("AutoCfg loading failed: %v", err)
    }
    
    // Stage 2: go-cfg handles flag processing with clean naming
    // Generates: --service-name, --api-host, --database-port, etc.
    if err := cfg.FlatNest(&config); err != nil {
        log.Fatalf("Flag processing failed: %v", err)
    }
    
    // Configuration is now fully loaded with proper precedence:
    // Files (lowest) → Environment → Flags (highest)
}
#+end_src

*** Advantages
- **Immediate Implementation**: No major refactoring required
- **Clear Separation**: Each system handles its strengths
- **Backward Compatibility**: Existing code continues to work
- **Low Risk**: Minimal architectural changes

*** Disadvantages
- **Dual Dependencies**: Applications must import both packages
- **Potential Conflicts**: Different struct tag interpretations
- **Configuration Duplication**: Some settings may need to be specified in both systems

// Enhanced go-cfg with integrated AutoCfg-style discovery
package cfg

type ConfigOptions struct {
    SearchMode   SearchMode
    SearchPaths  []string
    EnvOverride  string
    ProgramName  string
}

type SearchMode int
const (
    Union SearchMode = 1 << iota  // Merge all found configs
    First                        // Stop on first found  
    Direct                       // Load direct config files
    Indirect                     // Load via pointer files
)

// Enhanced FlatNest with discovery options (IMPLEMENTED)
func FlatNestWithDiscovery(opts ConfigOptions, ptrs ...interface{}) error

// Simple API maintaining backward compatibility (IMPLEMENTED)
func FlatNest(ptrs ...interface{}) error {
    return FlatNestWithDiscovery(DefaultConfigOptions(), ptrs...)
}

// Default configuration for most use cases (IMPLEMENTED)
func DefaultConfigOptions() ConfigOptions {
    return ConfigOptions{
        SearchMode:  Union | Direct,
        EnvOverride: "AUTOCFG_FILENAME",
    }
}
#+end_src

*** Discovery Modes in Detail
**** Union Mode (Default)
Merges all found configuration files in search order:
1. System configuration (=/etc/{program}/config.json=)
2. User configuration (=~/.config/{program}/config.json=)
3. Local configuration (=.{program}.json=)
4. Current directory (=config.json=)
5. Environment variables
6. Command line flags

**** First Mode
Stops at the first found configuration file, providing traditional AutoCfg behavior.

**** Indirect Mode
Supports AutoCfg pointer files with format:
#+begin_src json
{
  "path": "/secure/config.json",
  "env": {
    "DATABASE_HOST": "prod-db.internal",
    "API_SECRET": "production-secret"
  }
}

package main

import (
    "log"
    "github.com/davidwalter0/go-cfg"
)

type Config struct {
    ServiceName string `json:"service_name" required:"true"`
    API struct {
        Host string `json:"host" default:"localhost"`
        Port int    `json:"port" default:"8080"`
    } `json:"api"`
}

func main() {
    var config Config
    
    // Enhanced go-cfg with AutoCfg patterns integrated
    opts := cfg.ConfigOptions{
        SearchMode: cfg.Union | cfg.Direct,  // Merge all found configs
        SearchPaths: []string{
            "/etc/myapp/config.json",
            "~/.config/myapp/config.json", 
            ".myapp.json",
        },
        EnvOverride: "MYAPP_CONFIG_FILE",
    }
    
    if err := cfg.FlatNestWithDiscovery(opts, &config); err != nil {
        log.Fatalf("Configuration failed: %v", err)
    }
    
    // Single API call handles:
    // - File discovery and loading (AutoCfg patterns)
    // - Environment variable processing  
    // - Clean flag generation (go-cfg strengths)
    // - Validation and help text
}

*** Unified API Design
#+begin_src go :tangle /home/david/org/go-cfg/doc/unified-api-example.go :results org :main no :package 'discard :mkdirp yes :tangle-mode o0644
package main

import (
    "log"
    "github.com/davidwalter0/go-cfg/v2"
)

type Config struct {
    ServiceName string `json:"service_name" required:"true" help:"Service identifier"`
    API struct {
        Host string `json:"host" default:"localhost" help:"API server host"`
        Port int    `json:"port" default:"8080" help:"API server port"`
    } `json:"api" help:"API server configuration"`
}

func main() {
    var config Config
    
    // Unified configuration with all features
    mgr := cfg.NewManager().
        WithDiscovery(cfg.Union | cfg.Direct).
        WithFlagStyle(cfg.FlatNest).
        WithValidation(true).
        WithHelpEnhancement(true)
    
    if err := mgr.Configure(&config); err != nil {
        log.Fatalf("Configuration failed: %v", err)
    }
    
    // Or simple API for common cases
    if err := cfg.Configure(&config); err != nil {
        log.Fatalf("Configuration failed: %v", err)
    }
}

- Maintain existing struct tag formats (=json=, =default=, =required=)

- Keep go-cfg flag naming and help generation
- Support both JSON and YAML configuration files

** Performance Implications
- **Layered Integration**: Minimal overhead, two separate processing passes
- **Pattern Adoption**: Slight overhead from unified processing
- **Unified Architecture**: Optimal performance, single integrated pass

This phased approach allows for incremental value delivery while managing risk and ensuring user adoption at each stage.
